## 2. Agent Inventory & Workflow Nature

### Question 1: Which agents are implemented?
The codebase implements four specialized agents/nodes:
1. **Classifier Agent** (`packages/agents/nodes/classifier.py`)
2. **Analyst Agent** (`packages/agents/agents/analyst.py`)
3. **Verifier Agent** (`packages/agents/agents/verifier.py`)
4. **Router Node** (`packages/agents/nodes/router.py`)

### Question 2: What is each agent responsible for?
- **Classifier:** Validates declared bidder category credentials (DPIIT startup certificates, Udyam numbers, consortium member thresholds, 5-year incorporation threshold from Annexure 1.A). Extracts normalized qualification metrics.
- **Analyst:** Evaluates mandatory tender eligibility conditions MC-01 through MC-09 against the procurement corpus using multi-hop retrieval strategies S1, S2, and S3. Identifies statutory relaxations and conflicting clauses.
- **Verifier:** An independent adversarial auditor that inspects every finding and citation generated by the Analyst against the immutable passage store, ensuring quotes are verbatim ($\le 38$ words) and supported by genuine corpus chunks.
- **Router:** A deterministic disposition table that evaluates findings and assigns the final advisory route (`PASS_TO_TECHNICAL_EVALUATION`, `SEEK_CLARIFICATION`, `REJECT_WITH_CITED_CONDITION`, `ESCALATE_TO_HUMAN`).

### Question 3: Are these genuine independent agent workflows or simply Python functions with agent labels?
**They are genuine stateful agent workflows.**  
The system maintains an explicit shared `AgentState` (`packages/agents/state.py`) passed across stages with checkpointing (`MemoryCheckpointer` in `packages/agents/checkpoint.py`), retry loops between Analyst and Verifier (up to `MAX_VERIFY_RETRIES=2`), strategy state progression (`S1` $\rightarrow$ `S2` $\rightarrow$ `S3`), and decoupled tool calling.

## 3. Orchestration Framework

### Question 11: Does the system use LangChain, LangGraph, CrewAI, AutoGen, direct API calls, or a custom orchestration framework?
- **Orchestration Framework:** The system uses a **custom LangGraph-compatible stateful graph topology** implemented in pure Python (`ScreeningWorkflow` in `packages/agents/graph.py`).
- It mimics LangGraph's node-and-edge state machine structure (`classify_bidder` $\rightarrow$ `analyst.analyze` $\leftrightarrow$ `verifier.verify` $\rightarrow$ `route_screening`) with state validation, transition routing, and state checkpoints, but avoids heavy external runtime dependencies, ensuring high execution speed and zero vendor lock-in.

## 5. Tools Invoked by Each Agent

### Question 10: Which tools does each agent invoke?

1. **Classifier Node:**
   - Pure rule-based entity extraction and contract validation. Invokes date calculations against incorporation date and checks document registries.
2. **Analyst Agent:**
   - `search_corpus(query, corpus_scope, top_k, applies_to)`: Semantic & keyword search over tender and policy documents.
   - `get_clause(clause_id)`: Exact clause retrieval by ID.
   - `find_modifying_provisions(clause_id, category)`: Relational lookup of statutory policy amendments (e.g. DoE OM 20-09-2016).
   - `check_threshold(condition_id, actual_value, unit)`: Quantitative comparison against tender parameters.
3. **Verifier Agent:**
   - `verify_citations(findings, retrieved_passages)`: Read-only access to session passage store; verifies verbatim text containment and length bounds.
4. **Router Node:**
   - Deterministic rule matrix lookup based on finding status flags.
